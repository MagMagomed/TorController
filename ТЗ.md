# Техническое задание: Tor Controller

## 1. Цель

Создать настольное приложение для Windows, которое обнаруживает установленные службы Tor, показывает их состояние и настройки, а также позволяет управлять службами и редактировать их конфигурацию.

## 2. Технологии и архитектура

- WPF, .NET, архитектура MVVM.
- Интерфейс и операции с файлами/службами не должны блокировать UI-поток.
- Данные хранить в локальных JSON-файлах, без SQL-сервера. Коллекции в JSON являются аналогом таблиц.
- При первом запуске создать необходимые файлы хранилища и справочники, затем запустить обнаружение служб.
- Не перезаписывать или удалять имеющиеся данные при запуске. Ошибки чтения/записи хранилища показывать явно.

## 3. JSON-модель данных

Хранить коллекции раздельно, например в `tor-services.json`, `stages.json`, `starting-types.json` и `configurations.json`. Точный каталог приложения определить при реализации; предпочтительно использовать каталог данных текущего пользователя.

### 3.1. `TorServices`

- `Id: Guid` — внутренний идентификатор записи приложения. Создаётся случайным Guid при добавлении записи; не используется для поиска Windows-службы.
- `Name: string` — уникальное системное имя Windows-службы, например `tor` или `Tor2`. По нему `TorServiceSeeker` определяет, есть ли служба в хранилище.
- `DisplayName: string` — отображаемое имя Windows-службы, например `Tor Win32 Service`.
- `Stage: Guid` — ссылка на `Stages.Id`, текущее состояние службы.
- `StartingType: Guid` — ссылка на `StartingTypes.Id`, режим запуска службы.
- `Configuration: Guid` — ссылка на `Configurations.Id`.
- `TorExecutablePath: string` — путь к `tor.exe`.
- `ConfigurationFilePath: string` — путь к используемому файлу `torrc`.
- `ServiceAccount: string` — учётная запись, от имени которой запускается служба, если доступна.

Системное имя службы уникально. При обнаружении уже известного `Name` обновлять изменившиеся сведения существующей записи, сохраняя её `Id`. При обнаружении нового `Name` создавать новую запись со случайным `Id`.

### 3.2. `Stages`

- `Id: Guid`
- `Name: string` — человекочитаемое состояние службы.

Предусмотреть состояния, соответствующие Windows Service Control Manager, как минимум: `Running`, `Stopped`, `StartPending`, `StopPending`, `Paused`, `Unknown`. Состояния хранить в справочнике; записи Tor ссылаются на них по Guid.

### 3.3. `StartingTypes`

- `Id: Guid`
- `Name: string` — режим запуска Windows-службы, например `Automatic`, `Automatic (Delayed Start)`, `Manual`, `Disabled`, `Unknown`.

### 3.4. `Configurations`

- `Id: Guid`
- `SocksPorts: integer[]` — все директивы `SocksPort`.
- `SocksPortEndpoints: string[]` — полные аргументы директив `SocksPort`, включая адрес привязки и дополнительные параметры. Используются при сохранении, чтобы редактирование не меняло сетевую привязку или флаги; `SocksPorts` содержит извлечённые TCP-порты для отображения.
- `UseBridges: bool` — значение директивы `UseBridges`.
- `ClientTransportPlugins: string[]` — все директивы `ClientTransportPlugin`.
- `Bridges: string[]` — все директивы `Bridge`.
- `Logs: string[]` — все настроенные назначения `Log`.
- `ControlPorts: integer[]` — все директивы `ControlPort`, если заданы.
- `ControlPortEndpoints: string[]` — полные аргументы директив `ControlPort`, включая адрес привязки и дополнительные параметры, для безопасного round-trip редактирования.
- `DataDirectory: string?` — значение директивы `DataDirectory`, если задано.
- `AdditionalDirectives: object` — прочие поддерживаемые несекретные директивы, которые нужно сохранить при чтении и редактировании.

Чтение и сохранение конфигурации не должно включать в отчёты или журналы значения паролей, ключей, cookie и других секретов. Неизвестные/секретные директивы нельзя без предупреждения отображать как обычные параметры.

Идентификаторы справочников и конфигураций создаются случайными Guid при создании соответствующих записей, сохраняются в JSON и не должны генерироваться заново при каждом запуске. Ссылки между записями проверяются при чтении; повреждённые или отсутствующие ссылки сообщаются явно.

## 4. Начальные данные

- При первом запуске создать пустые коллекции служб и конфигураций, а также заполнить справочники состояний и типов запуска.
- Не встраивать в исходный код или начальные JSON-файлы реальные локальные пути, учётные записи, параметры мостов, ключи, адреса или иные сведения об окружении пользователя.
- Сразу после загрузки приложения `TorServiceSeeker` обнаруживает установленные службы и добавляет актуальные сведения в локальное хранилище. Все пути и настройки берутся из системы и пользовательских файлов конфигурации, а не из предопределённых значений.

## 5. Обнаружение и обновление служб

Реализовать `TorServiceSeeker` с асинхронно вызываемым методом `Execute`, который:

1. Находит Windows-службы, связанные с Tor, и получает доступные системное/отображаемое имя, состояние, тип запуска, учётную запись и команду запуска.
2. По команде запуска определяет путь к `tor.exe` и аргумент `-f` с путём к `torrc`.
3. Читает конфигурацию и извлекает поддерживаемые несекретные параметры.
4. Сопоставляет службы с данными в JSON только по уникальному системному `Name`, не по Guid.
5. Добавляет ранее неизвестные службы и связанные записи справочников/конфигурации; обновляет существующие записи, если обнаружены изменения.
6. Не удаляет записи автоматически, если служба временно недоступна или не обнаружена.
7. Продолжает обработку остальных служб при частичной ошибке. По завершении возвращает `SeekResult { HasError: bool, Message: string }`; `Message` содержит понятное описание ошибок/предупреждений, включая частичные ошибки.

Ошибки доступа, отсутствующей конфигурации, некорректного файла или невозможности определить отдельное поле не должны скрываться за значениями по умолчанию. Сохранять достоверно полученные данные остальных служб и сообщать о неполных сведениях.

## 6. Интерфейс и загрузка

- Главный экран содержит таблицу «Сервисы» с именем службы, состоянием, типом запуска, путями и основными настройками.
- `ViewModel` предоставляет метод `OnLoad`, вызываемый при загрузке главного экрана.
- При загрузке сразу показать данные из JSON, параллельно запустить `TorServiceSeeker`, не блокируя интерфейс.
- После завершения обнаружения перечитать хранилище и обновить таблицу, включая частично найденные/обновлённые данные.
- Если `SeekResult.HasError == true`, показать `Message` над таблицей и всё равно показать актуальные успешно сохранённые данные. Если ошибок нет, обновить таблицу без сообщения об ошибке.
- Использовать понятные состояния загрузки и явное отображение ошибок.

## 7. Управление службами и конфигурацией

- Для выбранной службы предоставить запуск, остановку и перезапуск, а также просмотр и редактирование поддерживаемых настроек `torrc`.
- Перед сохранением изменённой конфигурации создать резервную копию исходного файла, проверить новый файл командой установленного Tor `tor.exe --verify-config -f <путь-к-torrc>` и только при успешной проверке разрешить применение.
- Перезапуск после изменения конфигурации выполнять только после явного подтверждения пользователя.
- Если действие требует повышенных прав, запросить UAC для этого действия и показать понятную ошибку, если пользователь отказал или операция не удалась. Не требовать постоянного запуска всего приложения от администратора без необходимости.
- Проверять и показывать ошибки управления службой, чтения/записи файлов и проверки конфигурации; не сообщать об успехе, если операция фактически не выполнена.

## Доработка #1. Создание новых служб Tor

Добавить в главное окно действие «Создать службу Tor». Функция регистрирует новую службу Windows на основе уже имеющегося `tor.exe`; приложение не скачивает и не устанавливает дистрибутив Tor.

### Сценарий создания

1. Пользователь открывает форму создания и указывает:
   - уникальное системное имя службы Windows;
   - отображаемое имя;
   - путь к существующему `tor.exe`;
   - отдельный каталог данных новой инстанции;
   - начальный тип запуска;
   - параметры `torrc`, используя те же поддерживаемые поля, что и редактор конфигурации.
2. Приложение проверяет обязательные поля, допустимость системного имени Windows-службы, существование исполняемого файла и каталога, а также отсутствие службы с таким именем в Windows и JSON-хранилище (сравнение имён без учёта регистра).
3. Приложение создаёт отдельные каталог данных и файл конфигурации новой инстанции. Создаваемый `torrc` должен содержать как минимум директиву `DataDirectory` для этого каталога и заданные пользователем настройки. Конфигурация и каталоги новой инстанции не должны перезаписывать файлы существующих служб.
4. До регистрации службы приложение проверяет созданный `torrc` найденным `tor.exe` командой `--verify-config -f <путь-к-torrc>`. При неуспешной проверке служба не регистрируется; пользователю показывается ошибка проверки.
5. После успешной проверки приложение с явным согласием пользователя запрашивает повышение прав UAC только для регистрации службы. Служба регистрируется в Windows Service Control Manager с командой запуска указанного `tor.exe` в режиме Windows-службы (`--nt-service`) и ссылкой `-f` на созданный `torrc`; выбранный тип запуска применяется при регистрации.
6. После подтверждённой Windows регистрации приложение запускает `TorServiceSeeker`, сохраняет сведения о новой службе и её конфигурации в JSON и обновляет таблицу. Запись сопоставляется по системному имени; её Guid и связанные Guid создаются один раз и сохраняются.
7. Регистрация и первоначальный запуск — отдельные действия: новая служба не запускается автоматически при создании. Запускать её можно существующей командой управления службами.

### Выбор пути к `tor.exe`

- На форме создания вместо обычного поля пути предоставить выпадающий список с предложенными путями к `tor.exe`, обнаруженными у уже известных приложению Tor-служб.
- Убирать повторяющиеся пути без учёта регистра и предлагать только пути, по которым файл `tor.exe` существует на момент открытия формы.
- Пользователь может выбрать предложенный путь или указать другой путь вручную; выбранное или введённое значение проходит ту же проверку абсолютного пути и существования файла до создания службы.
- Если доступных предложений нет, список остаётся пустым, а пользователь всё равно может ввести путь вручную.
- Не выполнять полный поиск по дискам для построения списка предложений.
- Покрыть тестами формирование предложений, удаление дубликатов, исключение отсутствующих файлов, пустой список и ввод собственного пути.

### Ошибки, отмена и безопасность

- Отмена пользователем UAC или ошибка валидации/проверки/создания файлов/регистрации службы должны быть явно показаны; приложение не должно сообщать об успешном создании, если служба не зарегистрирована.
- Если подготовка файлов прошла, но регистрация службы не удалась, сообщить о созданных путях. Удалять подготовленные файлы автоматически запрещено; пользователь может проверить их и удалить самостоятельно.
- Если служба зарегистрирована, но последующее обнаружение или сохранение JSON завершилось ошибкой, сообщить, что служба уже создана в Windows, и предоставить её системное имя для дальнейшего обновления через повторное обнаружение. Не выполнять скрытую регистрацию повторно.
- Проверять, что указанная конфигурация не включает содержимое приватных ключей, паролей или cookie в сообщения, JSON, журналы приложения и UI.
- Повторная попытка создания с уже зарегистрированным системным именем должна быть отклонена без изменения существующей службы и её файлов.

### Тестирование и критерии приёмки

- Для каждого нового production-класса создания службы создать отдельный класс MSTest v2; покрыть валидацию, конфликты имён, генерацию конфигурации, проверку `tor.exe`, UAC, регистрацию, частичные ошибки и сохранение JSON.
- Использовать внедряемые mock/fake-зависимости для Windows Service Control Manager, запуска `tor.exe`, файловой системы, хранилища и подтверждения UAC. Тесты не должны регистрировать службы, запускать UAC или изменять реальные файлы и службы.
- Успешный сценарий завершается одной зарегистрированной, но остановленной службой, отдельным `torrc` и каталогом данных, корректными JSON-ссылками и обновлённой строкой таблицы.
- Любая ошибка до регистрации оставляет существующие службы и их конфигурации нетронутыми; повторный запуск обнаружения не создаёт дубликатов.

## Доработка #2. Подсказки полей формы создания Tor-службы

Добавить поясняющие всплывающие подсказки к полям формы создания службы Tor.

### Требования

- При наведении указателя мыши на каждое поле ввода формы показывать всплывающую подсказку на русском языке.
- Подсказка объясняет назначение поля, зачем нужен соответствующий параметр и на что он влияет, ожидаемый формат или тип данных и содержит пример заполнения. Для переключателя использования мостов поясняет действие включённого и выключенного состояний и когда их выбирать.
- Добавить подсказки для системного имени службы, отображаемого имени, пути к `tor.exe`, каталога данных, типа запуска, SOCKS-портов/адресов, переключателя мостов, списка мостов, `ClientTransportPlugin`, журналов и Control-портов/адресов.
- Примеры должны быть синтетическими и безопасными: не использовать реальные адреса мостов, секреты, пароли, ключи или пользовательские пути/данные.
- Подсказка должна соответствовать конкретному полю и быть доступна при наведении на него. Её отображение не меняет введённые значения или поведение формы.

### Тестирование и критерии приёмки

- UI-тестами проверить наличие содержательных подсказок у всех перечисленных полей и соответствие каждой подсказки нужному контролу.
- Проверить, что подсказки содержат назначение параметра, зачем он нужен или на что влияет, ожидаемые данные и синтетический пример, а подсказка переключателя мостов описывает оба состояния.
- Убедиться, что подсказки не содержат реальных пользовательских путей, адресов мостов или секретных данных.

## Доработка #3. Удаление Tor-служб

Добавить возможность удалить выбранную Tor-службу из Windows и из списка приложения.

### Требования

- Добавить действие удаления выбранной службы на главном экране. Если служба не выбрана, действие недоступно.
- До любых изменений показать подтверждение с системным именем и отображаемым именем службы. Если приложение владеет созданными им файлами этой службы, также показать путь к `torrc` и каталог данных и явно предупредить, что каталог данных со всем содержимым будет удалён; исполняемый файл Tor, транспортные плагины и журналы за пределами каталога данных останутся. Если служба была только обнаружена, сообщить, что её файлы останутся на диске.
- После подтверждения, если служба запущена, сначала остановить её. При ошибке остановки отменить удаление и сохранить регистрацию и данные приложения без изменений.
- Запрашивать повышение прав UAC только для удаления регистрации службы через Windows Service Control Manager. Не требовать постоянного запуска приложения от администратора.
- Удалять регистрацию службы Windows по системному имени. Если Windows сообщает об ошибке, не удалять запись и конфигурацию из JSON; показать понятную ошибку.
- Хранить в записи `TorServices` явный признак того, что приложение создало отдельный каталог данных и `torrc` этой службы. Выставлять его только для службы, зарегистрированной через `TorServiceCreator`; для ранее обнаруженных служб и старых записей без признака считать файлы пользовательскими.
- Только после подтверждённого удаления службы из Windows удалять созданный приложением файл `torrc` и отдельный каталог данных со всем содержимым, и только если признак владения установлен. Удалять их только по путям, сохранённым для выбранной службы; перед удалением проверить, что эти пути не совпадают и не пересекаются с исполняемыми файлами, конфигурациями, каталогами данных или журналами других сохранённых служб. Не удалять корневые каталоги, общие каталоги, `tor.exe`, транспортные плагины и журналы за пределами каталога данных.
- Только после успешной очистки файлов удалить запись службы из `TorServices` и обновить список в интерфейсе.
- Удалить запись конфигурации из JSON только если на неё больше не ссылается ни одна служба. Не удалять справочники `Stages`/`StartingTypes`, файлы конфигурации и каталоги данных других служб, журналы за пределами каталога данных выбранной службы или `tor.exe`.
- Сохранять в записи службы признак того, что регистрация Windows уже удалена, прежде чем начинать очистку файлов и JSON. При повторной попытке или после перезапуска приложения пропускать остановку и удаление Windows-службы, если этот признак установлен.
- Если удаление регистрации Windows прошло успешно, но сохранение признака, очистка файлов или обновление JSON завершились ошибкой, явно сообщить о частичном результате и системном имени уже удалённой службы; не сообщать о полном успехе. Если признак удалось сохранить, оставить запись и необходимые пути для повторной очистки/синхронизации.
- Если путь к `torrc` или каталогу данных отсутствует, неоднозначен, разделяется с другой службой либо проверка безопасности пути не проходит, не удалять файлы по этому пути; сообщить, какие файлы оставлены и почему.
- Обновить таблицу и выбор службы после успешного удаления; при частичной ошибке отобразить актуальные данные и понятное сообщение.

### Тестирование и критерии приёмки

- Покрыть отдельными MSTest v2 проверками подтверждение/отказ пользователя, недоступность команды без выбранной строки, остановку работающей службы, отказ остановки, отказ UAC, ошибку Windows при удалении, успешное удаление и частичную ошибку JSON.

- Проверить удаление `torrc` и отдельного каталога данных со всем содержимым только для созданной приложением службы; сохранность файлов ранее обнаруженной службы, `tor.exe`, транспортных плагинов и журналов вне каталога данных; запрет удаления общих/пересекающихся путей; удаление только неиспользуемой записи конфигурации и сохранение конфигурации, используемой другой службой.
- Проверить, что при ошибке очистки данных приложение сообщает о частичном результате и повторяет очистку без повторного удаления Windows-службы.
- Тесты должны использовать fake/mock службы, файловое хранилище и подтверждение; не управлять реальными службами Windows и не запускать UAC.

## 8. Модульные тесты

- Создать отдельный проект тестов на MSTest v2 (`MSTest.TestFramework` и `MSTest.TestAdapter` версии 2.x), включить его в решение и запускать тесты стандартным `dotnet test`.
- Для каждого исходного production-класса создать отдельный класс тестов с соответствующим именем, например `TorServiceSeekerTests` для `TorServiceSeeker`. Не объединять тесты разных production-классов в один класс тестов.
- Покрыть тестами каждый метод каждого исходного production-класса, включая `ViewModel`, модели с собственной логикой, сервисы, обработчики событий и методы code-behind. Для свойств и конструкторов, содержащих логику или валидацию, также предусмотреть проверки. Сгенерированный компилятором и WPF/XAML код отдельно не тестировать.
- Тесты должны использовать mock/fake-зависимости и тестовые данные; не обращаться к реальным службам Windows, UAC, пользовательским JSON-файлам, реальному `tor.exe`, сети или каталогам установки Tor. Файловое хранилище тестировать в изолированном временном каталоге с mock JSON-данными.

Использовать внедрение зависимостей, чтобы тесты могли заменять эти компоненты mock/fake-реализациями.

Для `TorServiceSeeker` проверить добавление новой службы, обновление службы по `Name` без изменения её `Id`, отсутствие дубликатов при повторном поиске, несколько служб, частичные ошибки и сохранение достоверно полученных данных.

Использовать управляемые mock-ответы и проверку порядка/асинхронного завершения операций.

## 9. Безопасность и критерии приёмки

- Не считывать и не показывать содержимое приватных ключей, cookie авторизации или паролей; не сохранять их в JSON, логах или UI.
- Не использовать Guid для определения, существует ли Windows-служба; использовать её системный `Name`.
- Повторный запуск приложения не создаёт дубликаты служб, справочников или конфигураций и не меняет неизменившиеся Guid.
- Первая и последующие загрузки отображают доступные сохранённые данные без блокировки интерфейса; обнаруженные изменения отражаются в таблице.
- Ошибка для одной службы не мешает обработке остальных и явно отображается пользователю.
- Обновление конфигурации сохраняет резервную копию и не применяется при неуспешной проверке.
- Отказ UAC и ошибки Windows-служб/файлов сообщаются явно, без ложного подтверждения успеха.
- Для каждого исходного production-класса есть отдельный соответствующий класс MSTest v2; тесты охватывают все его методы и UI-сценарии на mock-данных.
- `dotnet test` запускает тестовый проект; тесты не изменяют настоящие службы, файлы конфигурации, данные приложения или состояние ОС.
